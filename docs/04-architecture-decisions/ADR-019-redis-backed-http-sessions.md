# ADR-019: Redis-backed shared HTTP sessions

- **Status:** Accepted for Phase 4
- **Context:** The API must share authenticated sessions across replicas without moving credentials into browser tokens or weakening CSRF.
- **Decision:** Use Spring Session Data Redis, managed by Spring Boot 4.1.2. Redis is reached only on the private Compose data/application network. Session namespace and idle timeout are configurable; default namespace is `cloudresilience:sessions`, timeout 30 minutes, immediate repository flush and periodic expired-session cleanup. Cookie remains HttpOnly, SameSite=Lax, Secure configurable (false only for local HTTP), path `/`, and named `JSESSIONID`.
- **Serialization/security:** Use a Jackson 3 JSON serializer with Spring Security's Jackson modules and `BasicPolymorphicTypeValidator`; only Spring Security's approved types plus the application `UserPrincipal`, `RoleName`, and required JDK collection implementations are accepted. A serializer round-trip and rejection test covers SecurityContext restoration and unapproved runtime types. Session principal is explicitly `Serializable` and sanitized after password authentication: password hash and credentials are not retained. Redis is not host-published by Compose. Protect Redis with network isolation and a deployment-specific secret; do not expose the Redis protocol publicly.
- **Lifecycle:** Existing `ChangeSessionIdAuthenticationStrategy` rotates the ID at login. Logout invalidates the shared record. Redis expiration is the idle-session expiration source and matches servlet timeout.
- **Failure policy:** No local-session fallback. Redis readiness participates in API readiness; session-backed requests fail closed with generic 503 if Redis is unavailable. See ADR-022.
- **Consequences:** Any API replica can resolve/invalidate sessions, but Redis remains a single local service in Compose and is not an HA/failover claim. Redis loss interrupts authentication until service recovers; session persistence across container restart depends on its local AOF volume and is not a backup guarantee.
- **Verification:** Real two-server Testcontainers integration test exercises login on A, identity on B, B restart, B logout invalidating A, Redis TTL expiry and outage handling. Execution depends on Docker availability.
